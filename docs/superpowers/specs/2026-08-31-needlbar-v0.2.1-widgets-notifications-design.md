# Needlbar v0.2.1 Widgets and Notifications Design

**Status:** User-approved written design; implementation not started.

**Scope:** v0.2.1 only.

## 1. Purpose and Roadmap Position

v0.2.1 adds a single native macOS Overview widget and optional local quota threshold
notifications. It follows the completed v0.2.0 local JSON export implementation and precedes any project, commit, or pull-request cost analytics.

The feature makes the current normalized Needlbar state glanceable outside the
menu-bar popover. It does not make WidgetKit a data source, alter a provider
integration, or change Needlbar's local-first privacy model.

This document is an amendment to the approved v0.1 architecture and the approved v0.2.0
export design. Those documents remain authoritative where this document is silent. In particular, the v0.2.0 JSON export schema and behavior are unchanged.

## 2. Product Scope

### 2.1 Included

- One native macOS **medium** Overview widget.
- Fixed provider treatment for Claude, Codex, and Cursor.
- Claude and Codex remaining quota and reset time as the primary content.
- Today token usage and estimated cost as compact secondary content.
- Last-known-good display data, explicit freshness state, and a fixed deep link into the Needlbar Overview.
- Opt-in, local, app-running-only Claude/Codex quota threshold notifications.

### 2.2 Excluded

- Small, large, accessory, provider-specific, configurable, or interactive widgets.
- A widget-initiated provider/source refresh, provider login, Keychain read, bridge call, source scan, network request, Rust change, C ABI change, or authentication flow.
- Cursor subscription quota, Cursor credential handling, or Cursor remote access. Cursor remains local-cache usage only.
- A background daemon, scheduled monitor, backend, cloud sync, account,
  telemetry, analytics history, webhook, or notification action.
- New providers, release tags, or public-release actions.

## 3. User Experience

### 3.1 Overview Widget

The Widget Gallery exposes exactly one Needlbar medium widget named **Overview**. Its fixed layout contains:

1. A title and freshness/last-updated indicator.
2. A Claude quota row and a Codex quota row, each showing a safe provider label, the selected headline window's remaining percentage, fixed local window-category label, and its reset time when currently meaningful.
3. A fixed **Cursor — Quota unavailable** row. It states that Cursor contributes local cached usage only and never shows a remaining-quota gauge or reset.
4. A compact secondary today-usage summary for the fixed three-provider set: total tokens and estimated cost.

For Claude and Codex independently, the headline window is the allowlisted
window with the smallest remaining percentage. The allowlist is
`claude.session`, `claude.weekly`, `codex.primary`, and `codex.secondary`, each
restricted to its matching provider. A tie is resolved by its stable
allowlisted window ID in deterministic lexical order. The selection is
independent of menu-bar module toggles. The widget maps that known ID to a
fixed local category label; it never presents the provider's raw window title.

The widget does not expose raw provider window titles, error messages,
account names, paths, prompt content, credentials, or source content.

When a supported quota is unavailable or requires authentication and no
displayable value exists, the row says **Quota unavailable**. It never
substitutes zero remaining or an invented reset. Cursor's quota is always
unavailable and is not presented as a quota gauge.

Tapping/clicking any widget region opens only the fixed allowlisted URL
`needlbar://overview`. The URL has no provider identifier, user-controlled
parameter, refresh instruction, or login action. Opening it can show the
existing app UI; it does not promise a refresh.

### 3.2 Freshness and Staleness

The main app maps the existing independently refreshed usage and quota streams
into the widget projection. A quota row is fresh only when its quota stream is
fresh. A usage summary is fresh only when its usage stream is fresh.

The display age is measured from each stream's real last successful sample,
not from a projection rewrite or WidgetKit timeline reload. The widget's age
horizon is 15 minutes, equal to three existing five-minute safety-refresh
intervals: an age below 15 minutes is fresh; an age at or above 15 minutes is
stale. For a stale or failed stream, the widget preserves the last good value
and clearly labels it **Stale** with its last-updated time.

If there is no last good value, the widget shows unavailable state. A failed
or stale quota must not blank valid usage, and a failed or stale usage must not
blank valid quota. The host's exit preserves the last successfully written
projection for the widget; no value is promoted to fresh merely because the
host is no longer running.

`resetsAt` is display information. A null reset remains absent. A reset time
that has passed is rendered as **Awaiting fresh reading**, even if the previous
stream status was fresh, rather than assuming 100% remaining or deriving a
replacement reset time.

The today usage summary observes the user's local calendar-day boundary. On a
new local day it does not display a prior day's `today` counters while waiting
for a fresh usage sample; it uses a neutral unavailable/pending presentation
instead.

### 3.3 Settings

Settings adds one Notifications section. Quota notifications are **Off** by
default. The user explicitly turns on the one quota-alert preference before
Needlbar requests macOS notification authorization.

If authorization is denied or later revoked, the preference is inactive and
the Settings UI explains that notifications are unavailable. It may offer a
user-initiated route to System Settings; it does not repeatedly prompt or
attempt to work around the operating system's decision. Turning the preference
off stops evaluation and does not erase previously recorded de-duplication
state.

## 4. Architecture and Ownership

### 4.1 Existing State Remains the Source of Truth

`ProviderSnapshotStore` remains the actor-isolated owner of the app's
independent provider usage/quota values, statuses, last-success timestamps,
and update stream. `RefreshCoordinator` and the existing repositories remain
the only components that refresh sources or invoke existing provider/auth
paths.

No widget, extension, notification path, or shared-file reader invokes the
Rust bridge, C ABI, provider adapter, source synchronizer, Keychain, login
flow, local source parser, or network. Usage and quota remain independently
refreshable and independently fallible.

### 4.2 Sanitized Shared Projection

The main app observes the store during its own lifetime and maps snapshots to
a small, versioned widget projection. The projection is a presentation DTO,
not an export document and not a copy of raw provider state. It contains only:

- fixed provider identities `claude`, `codex`, and `cursor` where needed;
- allowlisted headline quota window identity, remaining percentage, fixed
  local category label, and nullable reset timestamp for Claude/Codex;
- per-provider usage status, local usage-day key, and usage last-success
  timestamp, plus the corresponding quota status/timestamp;
- the bounded today token/cost summary necessary for the widget; and
- a schema version suitable for safe rejection of unknown data.

The today summary uses checked integer token addition and checked `Decimal`
cost addition over available current-local-day provider usage. With no available
contributors the summary is **Unavailable**; with some contributors missing it
is **Partial**; and the
summary is fresh only when every displayed contributor is fresh. Per-provider
usage timestamps/statuses and the day key remain in the DTO so a newer source
cannot hide a stale contributor behind an aggregate's latest timestamp. Cursor
is labelled locally cached: its usage `lastSuccessfulAt` is cache-read time,
not a claim about provider-side currency.

The mapping validates finite values, nonfuture successful timestamps, local
day keys, known provider/window identities, and the bounded aggregate. It
rejects malformed projection input and emits no raw titles, diagnostics,
messages, account identifiers, secrets, cookies, authentication tokens, URLs, paths, prompt
text, source text, or provider payloads. Unknown schema versions, corrupted
bytes, impossible percentages, or unknown IDs decode as unavailable rather
than displaying guessed data.

The complete encoded projection is capped at 64 KiB and is written through a
private `0600`, same-directory temporary file followed by atomic replacement
in the App Group. The file is local and contains no credential or Keychain
material. The widget extension reads only this file and is resilient to a
missing, partial, malformed, or newer-version file by rendering unavailable.
Projection write/validation failures affect the widget only: they leave the
existing app snapshots and v0.2.0 export behavior untouched.

The widget target contains a pure DTO/decoder/display layer and must not
transitively link `NeedlbarCore`, `CNeedlbar`, or Rust merely because the host
Core target links the bridge. The host owns all Core mapping and all lifetime
observation; the extension owns no shared mutable business state.

### 4.3 WidgetKit Update Boundary

After a changed, accepted atomic projection write, the running host may make a
coalesced request for WidgetKit to reload the Overview widget's timelines.
Timeline entries re-evaluate the next freshness deadline, local midnight, and
display-only reset deadline without provider queries. WidgetKit chooses actual
rendering cadence; v0.2.1 promises neither real-time update nor exact reload
timing, and no background refresh. The extension's timeline always reads local
shared state and never causes a source refresh.

This follows Apple's WidgetKit update model in
[Keeping a widget up to date](https://developer.apple.com/documentation/widgetkit/keeping-a-widget-up-to-date/).
The App Group container follows Apple's macOS guidance in
[Accessing app group containers](https://developer.apple.com/documentation/xcode/accessing-app-group-containers).

### 4.4 Packaging and Entitlements

Implementation retains the present SwiftPM host and Rust build/test flow. It
adds the smallest separately built, embedded WidgetKit extension necessary for
macOS distribution; it does not require a wholesale host-project rewrite.
Exact packaging/project-file mechanics belong to the implementation plan.

The host remains unsandboxed because existing approved provider local reads
require that boundary. The WidgetKit extension receives App Sandbox and App Group
entitlements; it requires no network or Keychain entitlement.
The shared App Group identifier uses the TeamID-prefixed macOS-only convention
for the configured build team; implementation does not modify Apple portal
state. Extension embedding, entitlement matching, and Developer ID signing
must be verified on macOS 14 arm64 before acceptance.

## 5. Notification Semantics

### 5.1 Eligibility and Permission

The notification evaluator is serialized and runs only in the running main
app, after the user has enabled alerts and macOS authorization is currently
granted. It accepts only a new successful Claude or Codex quota sample,
identified by that quota stream's last-success sample identity; an unrelated
usage update cannot trigger an evaluation. The sample must have fresh quota
status, a nonfuture last-success timestamp, and age below 15 minutes, using the
same exact freshness limit as the widget. It never evaluates Cursor quota,
stale data, an error, authentication-required state, unavailable state, or a
cached widget projection.

The evaluator rechecks the preference and lifecycle generation after asynchronous
work and before reservation/submission. It obtains current OS authorization before
submission; the OS remains responsible for enforcing any subsequent revocation.
Stopping the app, turning alerts off, or re-enabling
alerts invalidates prior pending evaluation work; an old evaluation cannot
submit after that lifecycle change.

There are no app-scheduled future alerts, repeating schedules, background
tasks, notification service extensions, provisional-permission escalation,
sounds, badges, or delivery retries. A notification already submitted to the
operating system can still be delayed, coalesced, or suppressed by operating
system delivery policy or Focus; that is distinct from Needlbar scheduling
future alerts.

Notification copy is generic and privacy-safe, for example “Claude quota: 10%
or less remaining.” It uses fixed provider labels and local window-category
labels when useful and never
includes a raw window title, account data, token count, cost, reset timestamp,
error, or provider response.

Authorization behavior follows Apple's
[Asking permission to use notifications](https://developer.apple.com/documentation/usernotifications/asking-permission-to-use-notifications):
Needlbar requests it only from the explicit Settings enable action, not on
launch, refresh, widget render, or threshold observation.

### 5.2 Threshold and First-Sample Rules

Threshold stages are remaining quota **20%** and **10%**, inclusive. A stage
is eligible only on a downward crossing from above that stage during the
currently armed, evidenced quota cycle.

The first eligible fresh reading for a provider/window after enabling alerts or
after application restart establishes a baseline and sends no notification. If
it is already at or below 20% or 10%, the baseline consumes every stage already
reached while retaining any previously consumed flags. This prevents an
unexpected startup alert and prevents a later weaker alert for the same low
reading.

A fresh observation that falls from above 20% directly to 10% or lower submits
one 10%-remaining notification and consumes both the 20% and 10% stages. It
does not issue two alerts for that window's same observation or defer a 20%
alert until later. Distinct eligible windows are evaluated independently.

### 5.3 Durable, At-Most-Once Submission Ledger

A local durable ledger is keyed by known provider plus allowlisted quota-window
identity. It records enough nonsecret state to compare the last eligible quota
sample, track an observed cycle, and record reserved/consumed 20% and 10%
stages. It does not persist provider credentials, account identifiers, raw
provider titles, or source content.

The app reserves and durably persists a stage before submitting it to macOS.
It performs no retry after an uncertain submission result. With an intact
persisted ledger, this provides at-most-one local submission attempt per stage,
not guaranteed operating-system delivery and not whole-system exactly-once
behavior. If durable-ledger persistence fails, Needlbar suppresses rather than
sends a notification it cannot reliably de-duplicate.

On application restart, the first eligible sample establishes or validates a
baseline but does not erase recorded stage flags. A restart is never a new
cycle and cannot reissue a recorded submission. A missing or corrupt ledger
also begins a baseline and consumes currently reached stages; it cannot
reconstruct prior submissions, so the at-most-once guarantee depends on an
intact persisted ledger. Switching accounts cannot be reliably detected because
the design intentionally stores no account ID; no account-change de-duplication
guarantee is made.

### 5.4 Reset Evidence and Re-arming

`resetsAt` is not a provider-cycle identity and timestamp drift alone never
rearms an alert. A baseline may begin an observed cycle without a reset time.
When a valid future reset is first observed, the ledger pins it as that
observed cycle's anchor; later drift does not continuously replace the anchor.

Re-arming clears previously consumed flags only with conservative observed-cycle
evidence: the pinned prior future reset is now passed, a new eligible sample
has a future reset strictly later than the pinned anchor, and remaining quota
has freshly recovered above 20%. Numeric recovery alone cannot rearm. Once
re-armed, the new future reset replaces the pinned anchor and the recovered
reading establishes the new baseline; it sends no immediate alert.

A null, unknown, ambiguous, changed, or expired reset timestamp cannot itself
clear/rearm consumed stages. It does not suppress a legitimate first downward
crossing of a still-unconsumed stage (for example, a 10% crossing after the
20% stage was consumed). Instead, it blocks clearing/re-arming flags until the
conservative observed-cycle evidence exists. This is deliberately not a
guarantee of actual provider quota-cycle or account identity: a later real
cycle can be missed rather than inventing a potentially duplicate cycle.

## 6. Privacy and Security

The projection and ledger remain on the local machine and create no telemetry,
network request, backend record, cloud synchronization, or account. They do
not widen the approved provider-file or credential-read scope.

The widget's sandboxed extension reads only the private shared projection.
Neither the projection nor the notification text may contain secrets, authentication tokens,
cookies, credentials, account IDs, provider payloads, prompt/response/source
content, paths, raw errors, or arbitrary provider-provided strings.

## 7. Verification Expectations

Implementation must have pure fixture coverage for projection mapping,
validation, stale/age behavior, local-day rollover, and the full notification
state machine: first-low baselines, both threshold crossings, direct 10%
jumps, restart durability, reset drift, null/expired resets, denied permission,
and ledger write/submission failure suppression. Fixtures use synthetic
snapshots only; no live provider, credential, account, or usage data is needed.

macOS 14 arm64 acceptance must cover Widget Gallery discovery, widget render
and host-driven reload, stale preservation, host quit behavior, fixed deep
link opening, denied/revoked permission, alert de-duplication across restart,
and the absence of secret-bearing display/file content. It must also validate
extension-first build, embedding, entitlement matching, signing, and package
smoke behavior while preserving the existing `make test` verification path.

No technical acceptance in this section has yet occurred. Native signed-widget
acceptance on macOS 14 arm64 remains a prerequisite and is not proven by this
document.

## 8. Acceptance Summary

v0.2.1 is complete only when the one medium Overview widget reads the
sanitized host-written projection without refreshing or authenticating; it
preserves independently fresh/stale usage and quota semantics; Cursor quota is
unavailable; and notifications are opt-in, fresh-only, app-running-only,
privacy-safe, and durably de-duplicated under the conservative reset policy.

The work remains scoped to native macOS widget/notification presentation and
local state transfer. It does not modify provider behavior, Rust, the bridge,
authentication, or the v0.2.0 export contract.

No tag or release action is authorized.
