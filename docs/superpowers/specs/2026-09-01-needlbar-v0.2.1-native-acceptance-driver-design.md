# Needlbar v0.2.1 Native Acceptance Driver Design

**Status:** Approved Approach A design for implementation planning
**Date:** 2026-09-01
**Scope:** Acceptance-only support for the v0.2.1 native macOS 14 gate

## 1. Purpose and decision

The v0.2.1 widget and notification code is implemented and has automated
contract coverage, but automated tests and a macOS 26 host cannot establish
Widget Gallery, App Group, WidgetKit reload, or macOS notification behavior on
macOS 14. This design adds a deterministic, local fixture driver to a
separately built and Developer ID-signed acceptance artifact.

The driver supplies sanitized snapshots to the existing main-app state path.
It does not replace, mock, or bypass the components whose native behavior is
being accepted:

`ProviderSnapshotStore` → widget projection publisher → `WidgetCenter`, and
`ProviderSnapshotStore` → quota notification service → real local ledger →
`UNUserNotificationCenter`.

The driver is compiled only into the acceptance artifact. Normal development
builds, the public v0.2.2 artifact, and all release workflows exclude it and
do not recognize its launch argument. The public v0.2.2 signed artifact is
retained separately and remains the evidence source for production bundle,
entitlement, and production Widget Gallery checks.

## 2. Goals

1. Provide one explicit launch argument, `--acceptance-fixture <absolute-path>`,
   which selects a bounded sanitized fixture in the acceptance build.
2. Exercise the normal host lifecycle, store observation, App Group atomic
   projection writer, WidgetKit reload request, notification permission path,
   notification service, durable ledger, and OS UI on an actual macOS 14
   arm64 machine or VM.
3. Make widget and notification outcomes reproducible without provider
   accounts, credentials, browser sessions, source files, network access,
   Rust, the C ABI, Keychain, or export activity.
4. Capture bounded, redacted evidence that identifies the exact source,
   acceptance bundle, fixture digest, OS, signed entitlements, and observed
   outcomes without retaining secrets or raw provider data.
5. Keep the public v0.2.2 production artifact and its evidence independent of
   the fixture-enabled acceptance artifact.

## 3. Non-goals and immutable boundaries

- No change to provider adapters, source synchronization, authentication,
  browser login, Rust crates, the C ABI, Keychain access, export schema, or
  production refresh behavior.
- No provider, account, token, cookie, prompt, response, repository, path,
  or network data in a fixture.
- No acceptance-only button, menu item, settings row, debug panel, or public
  help text. The argument is the only driver entry point.
- No fixture support in normal, ad-hoc package, notarization, public release,
  or public UI builds.
- No direct App Group JSON injection, direct WidgetCenter invocation from the
  driver, fake notification client, fake ledger, notification database
  mutation, or OS permission database reset.
- No claim that a fixture-enabled artifact is the public v0.2.2 artifact or
  that a macOS 14 acceptance-driver result proves provider integrations.
- No tag, release, Apple portal mutation, notarization upload, or credential
  handling is authorized by this design.

## 4. Artifact and build isolation

### 4.1 Acceptance artifact

The acceptance package is built from the implementation commit that adds this
driver, with the acceptance-only compilation condition
`NEEDLBAR_ACCEPTANCE_DRIVER`. Its evidence records both that source commit and
the already-retained public v0.2.2 artifact's source commit; every
acceptance-specific code delta between them must be enumerated and
attributable to the driver or its tests. The host and WidgetKit extension are
built with the same macOS 14 arm64 minimum target and the same extension-first
packaging layout as production.
The extension contains no fixture code; only the host owns the driver.

The acceptance host and extension are signed separately, extension first, by
the configured Developer ID Application identity with hardened runtime and
the same App Group shape as production. The acceptance package is installed
in a disposable macOS 14 test VM or test account, never alongside the public
app bundle. The acceptance package is not notarization or release evidence;
its SHA-256 and strict nested signature verification are recorded only to
identify the test input.

The build contract must prove all of the following:

- the normal/public build has no `NEEDLBAR_ACCEPTANCE_DRIVER` code or
  `--acceptance-fixture` parser;
- the release workflow cannot select the acceptance condition or fixture
  files;
- the acceptance host alone contains the parser and driver symbols;
- the extension binary has no driver symbols or fixture dependency; and
- acceptance fixture files are not copied into the app bundle or any release
  artifact.

### 4.2 Public production artifact

Before installing the acceptance artifact, retain the downloaded public
v0.2.2 ZIP under the permitted `/Users/taejunoh/Developer/LFG` artifact area.
Use that exact ZIP for production evidence: checksum, arm64 executable,
Developer ID authority, hardened runtime, matching App Group entitlements,
extension embedding, and production Widget Gallery discovery. The public
artifact is never rebuilt with a fixture condition and is never replaced by
the acceptance package. A fixture result is not substituted for any public
artifact result.

## 5. Launch and fixture contract

### 5.1 Launch contract

The only accepted syntax is:

```text
Needlbar.app/Contents/MacOS/Needlbar --acceptance-fixture /absolute/path/fixture.json
```

The path must be absolute, resolve to one regular file beneath the disposable
acceptance input root established by the native-run harness, and be opened
read-only. The harness records that canonical root before launch. Relative
paths, additional arguments, symlinks escaping the input root, missing files,
directories, and duplicate driver arguments fail closed before app startup.
The argument is accepted only by a host compiled with
`NEEDLBAR_ACCEPTANCE_DRIVER`; a normal or public build contains no parser or
fixture-mode branch, so the spelling has no acceptance semantics there and
cannot activate fixture behavior.

The driver parses the fixture before starting `RefreshCoordinator`. In driver
mode it does not construct or start provider adapters, source synchronizers,
browser login, Keychain access, RustBridge/C ABI calls, export writers, or
network clients. It then starts the normal host-owned Core surfaces needed by
the acceptance: `ProviderSnapshotStore`, widget projection publisher,
`WidgetCenter` reload path, quota notification service, preferences, OS
authorization client, and the real `QuotaAlertLedgerStore` at its normal
Application Support location. The driver emits sanitized values through the
store's normal `applyUsage` and `applyQuota` APIs. It never writes the widget
projection or ledger itself.

The driver is a finite main-actor timeline. Each event is applied only after
the prior event's delay, and the store remains the sole source observed by the
publisher and notification service. A bounded fixture timeline makes host
reload and notification wake-up observable without adding a testing UI.

### 5.2 Fixture format

The fixture is UTF-8 JSON with no unknown keys. Its encoded size is at most
256 KiB; it has at most 32 events, provider rows are at most the fixed
Claude/Codex/Cursor set, and each event delay is finite and between 0 and
900 seconds. Timestamps are RFC 3339 values, finite, nonfuture relative to
the event clock, and use the fixture's explicit `timeZone` and `localDay`.
The parser rejects malformed JSON, duplicate keys, control characters,
unknown providers or windows, impossible percentages, negative tokens,
noncanonical day keys, future timestamps, overflow, and any field containing
credential/path/source-content canaries.

The accepted shape is:

```json
{
  "schemaVersion": 1,
  "timeZone": "America/New_York",
  "startAt": "2026-09-01T12:00:00.000Z",
  "events": [
    {
      "delaySeconds": 0,
      "localDay": "2026-09-01",
      "usage": {
        "claude": {"tokens": 800, "costUSD": "1.20"},
        "codex": {"tokens": 600, "costUSD": "0.90"},
        "cursor": {"tokens": 200, "costUSD": "0.30"}
      },
      "quota": {
        "claude": [{"id": "claude.session", "remainingPercent": 80, "resetsAt": "2026-09-02T12:00:00.000Z"}],
        "codex": [{"id": "codex.primary", "remainingPercent": 80, "resetsAt": "2026-09-02T12:00:00.000Z"}]
      }
    }
  ]
}
```

`usage` and `quota` values are canonical test values, not provider payloads.
The driver constructs fixed local labels and statuses required by the existing
domain models. The fixture has no raw window title, account field, URL, path,
message, diagnostic, credential, response, or source-content field. Cursor
may contribute local usage, but has no quota entry. A quota event must use
only `claude.session`, `claude.weekly`, `codex.primary`, or `codex.secondary`
with its matching provider.

The parser reports only one of these stable error codes and, when parsing an
event, its zero-based event index: `fixturePathInvalid`, `fixtureReadFailed`,
`fixtureTooLarge`, `fixtureMalformedJSON`, `fixtureUnknownKey`,
`fixtureDuplicateKey`, `fixtureInvalidValue`, `fixtureUnknownID`, or
`fixtureCanaryDetected`. Path and read failures use a null event index. It
never echoes fixture bytes, field values, absolute paths, or parser
diagnostics. A failed parse terminates the acceptance run before normal
providers or acceptance services start.

## 6. Native acceptance sequence

All sequences below run on macOS 14 arm64 with network access disabled at the
VM boundary. They use a fresh test user and a fresh App Group container for
each independent case. The operator records the acceptance bundle digest and
the public v0.2.2 digest separately.

### 6.1 Production Gallery and entitlement evidence

1. Install the downloaded public v0.2.2 artifact and verify its checksum,
   arm64 host/extension executables, Developer ID authority, hardened runtime,
   matching production App Group, extension point, and no network/Keychain
   entitlement.
2. Open Widget Gallery and search for `Needlbar`.
3. Record exactly one `Overview` widget with only the medium family and a
   rendered preview. Do not add or remove a user widget as part of this
   evidence unless the disposable test account is used.
4. Record that the public app has no acceptance argument or fixture resource.
5. Quit and remove only the disposable public-app installation before the
   acceptance-driver run. Preserve the downloaded public ZIP and evidence.

This is the production Gallery/entitlement result. The acceptance-driver
artifact is not used to rewrite or strengthen it.

### 6.2 Widget runtime and lifecycle

Use a fixture timeline containing a complete fresh state, a changed fresh
state, stale timestamps, reset-date cases, and a new local day. Malformed,
truncated, unknown-schema, and over-boundary fixture files are separate parser
preflight cases; they must fail before the normal host surfaces start.

1. Launch the acceptance host with the exact `--acceptance-fixture` argument.
   Confirm no provider/authentication/browser/Rust/C ABI/Keychain/export or
   network process is started, while the normal store and publisher start.
2. Add the single medium `Overview` widget in Widget Gallery and record its
   fixed Claude, Codex, Cursor, Today, and freshness presentation.
3. Allow the next fixture event to change a quota and usage value. Confirm the
   host's normal projection write has mode `0600`, bounded size, atomic
   replacement, and a `WidgetCenter` timeline reload request. Confirm the
   installed widget reflects the new sanitized value after WidgetKit chooses
   a render time; do not treat immediate rendering as guaranteed.
4. Advance a successful stream to just below 15 minutes and then exactly 15
   minutes old. Confirm the first remains Fresh and the second is Stale while
   preserving its last good value and timestamp. A failed quota must not blank
   valid usage, and a failed usage must not blank valid quota.
5. Supply a passed `resetsAt`; confirm the row says `Awaiting fresh reading`
   after the reset has passed rather than inventing 100% or a new reset.
6. Supply a new local day before a fresh usage event. Confirm the widget does
   not display the prior day's Today counters and instead shows its neutral
   pending/unavailable state. Then apply the new-day usage event and confirm
   the new summary.
7. Quit Needlbar and confirm the widget retains the last successfully written
   projection and does not promote it to Fresh or initiate a provider refresh.
8. Click the widget and confirm only `needlbar://overview` opens the normal
   Needlbar Overview. Confirm no provider, refresh, login, or user-controlled
   URL parameter is involved.

Before the native timeline run, execute the parser preflight with malformed,
truncated, unknown-schema, unknown-ID, and over-boundary files. Confirm each
returns only its stable error code and event index, starts no provider or
acceptance service, and leaves the App Group untouched. Widget decoder cases
for malformed or missing projection bytes remain covered by the existing
automated contract; this native sequence does not bypass the publisher by
writing projection bytes directly.

### 6.3 Notification permission and lifecycle

Each notification case starts with the real macOS authorization state recorded
from `UNUserNotificationCenter`. Permission changes are made only through
Needlbar Settings or System Settings; the permission database is never edited.

1. Launch the driver and open the normal Settings window. Confirm the quota
   alert preference is Off and no permission request occurs on launch,
   refresh, widget render, or settings-open alone.
2. Enable the preference through its normal Settings control. Confirm that
   only this explicit action requests macOS authorization. Exercise Deny and
   later Revoked states; confirm the preference becomes unavailable, no
   repeated prompt/workaround occurs, and no alert is submitted.
3. With authorization granted, apply the first fresh 80% Claude and Codex
   observations. Confirm they establish a baseline and submit no alert.
4. Apply a fresh inclusive 20% crossing. Confirm one generic provider/category
   alert is submitted and shown by macOS, with no token count, cost, reset,
   account, raw title, path, prompt, response, or source content.
5. Apply a fresh 10% observation after the 20% crossing. Confirm exactly one
   10% alert for that window. In a separate fresh cycle, jump directly from
   80% to 10% and confirm only the 10% alert is submitted; no deferred 20%
   alert is created.
6. Restart Needlbar while the sample remains low and confirm the durable
   ledger prevents a second submission. Restarting is not a new cycle.
7. Change only the reset date and repeat low observations. Confirm reset-date
   drift alone does not re-arm consumed stages.
8. For re-arm, let the pinned prior future reset pass, provide a strictly later
   future reset, and provide an eligible fresh reading recovered above 20%.
   Confirm that recovery establishes a no-alert baseline, then confirm a later
   downward crossing alerts once for the new cycle.
9. Make the normal `~/Library/Application Support/Needlbar` ledger destination
   non-writable in the disposable test account without replacing the ledger
   implementation. Apply a crossing and confirm no OS notification is
   submitted when reservation persistence fails. Restore permissions and
   confirm the next run starts from the safe baseline rules rather than
   guessing prior submission state.
10. Stop the app or turn alerts off while a permission, ledger, or submission
    operation is pending. Confirm lifecycle generation checks prevent a stale
    operation from submitting after stop/off/re-enable. No future schedule,
    background task, sound, badge, retry, or notification action is created.

## 7. Evidence and bounded failure handling

The acceptance harness writes evidence only under a disposable directory below
`/Users/taejunoh/Developer/LFG`. The evidence manifest contains:

- source commit, public artifact digest, acceptance artifact digest, macOS and
  Xcode versions, arm64 result, and safe signing/entitlement outcomes;
- fixture schema version and SHA-256, never fixture contents or user paths;
- step name, start/end time, pass/fail, stable error code, and bounded command
  exit status;
- screenshots of the disposable Widget Gallery/widget/Settings/notification
  surfaces with no account or credential data; and
- bounded filtered logs proving extension launch, WidgetCenter reload request,
  notification authorization state, ledger reservation ordering, and the
  absence of prohibited process/network paths.

Each command output is capped at 1 MiB, each screenshot is retained at native
resolution only when needed for a stated step, and all logs are filtered for
secret/path/account canaries before persistence. A failed step stops the
sequence, records its stable code, terminates only the acceptance app, and
leaves the public artifact untouched. Cleanup removes only the explicit
acceptance VM/app/fixture/evidence paths; it never removes a home directory,
repository, public ZIP, App Group data outside the disposable test account,
or signing material.

The final report must distinguish:

1. public v0.2.2 production Gallery/entitlement evidence;
2. acceptance-driver native behavior evidence; and
3. automated macOS 26/CI evidence.

Only the first two together can satisfy the combined v0.2.1 acceptance gate,
and neither changes the public release record.

## 8. Alternatives rejected

### 8.1 Directly inject projection JSON or notification ledger JSON

Rejected because it bypasses the host mapper, atomic writer, WidgetCenter reload
boundary, notification policy, reservation ordering, and decoder behavior that
the native gate must exercise.

### 8.2 Use fake WidgetCenter, UserNotifications, or ledger clients

Rejected because fakes are appropriate for unit tests already present, but they
cannot prove macOS 14 WidgetKit discovery, App Group readback, permission
policy, OS submission, or file-permission behavior.

### 8.3 Add a production debug screen or hidden public switch

Rejected because it expands public UI, risks fixture activation in a release
build, and creates an unreviewed production data injection path.

### 8.4 Use live Claude/Codex accounts or provider data

Rejected because it introduces credentials, network nondeterminism, provider
side effects, account identity, and privacy risk. It is also unnecessary for
the widget and notification contracts.

### 8.5 Put the driver in the public v0.2.2 artifact

Rejected because the public artifact must remain the production artifact. A
separate Developer ID acceptance build preserves production Gallery and
entitlement evidence while making the native behavior deterministic.

### 8.6 Treat macOS 26 or CI compilation as macOS 14 acceptance

Rejected because a compile or current-host smoke test cannot establish
macOS 14 Widget Gallery discovery, extension runtime, App Group readback, or
macOS notification permission behavior.

## 9. Acceptance criteria for this design

- The argument, compile condition, fixture schema, bounds, and failure codes
  are implemented exactly as specified.
- Normal/public builds contain no acceptance parser, fixture resource, or
  acceptance UI, and release scripts cannot select the acceptance condition.
- The acceptance build uses real production store, projection publisher,
  WidgetCenter, notification service, ledger, App Group, and OS permission
  paths.
- The native sequence records every widget and notification case in Sections
  6.2 and 6.3, including malformed data, quit, reset, midnight, denied/revoked
  permission, baseline, direct 10%, restart de-duplication, reset drift,
  re-arm, and ledger-write suppression.
- No prohibited provider/auth/Rust/C ABI/Keychain/browser/network/export path
  is started, read, or written by the driver.
- Evidence is bounded, sanitized, separately identifies public and acceptance
  artifacts, and remains under `/Users/taejunoh/Developer/LFG`.
- The public v0.2.2 signed artifact remains the production Gallery/entitlement
  evidence source; acceptance-driver results do not modify its release record.
