# Needlbar v0.2.1 Menu Panel Placement Design

**Date:** 2026-08-31

**Status:** Approved correction after native measurement
**Scope:** Replace only the menu presentation shell so the entire visible panel begins below the clicked menu-bar icon.

## Problem and Measured Root Cause

Needlbar used `NSPopover.show(relativeTo:of:preferredEdge:)`. The first correction selected
`.maxY` for a flipped status-bar button, but native measurement disproved that hypothesis:

- the real `NSStatusBarButton` was flipped;
- `.minY` and `.maxY` produced the same popover window and content frames;
- the SwiftUI content began below `NSScreen.visibleFrame.maxY`;
- macOS 26 still drew the system popover glass and arrow inside the menu-bar region.

`preferredEdge` is therefore only a placement preference and cannot enforce the product
requirement. `positioningRect` and SwiftUI padding also cannot constrain AppKit's window chrome.
The prior edge-selection implementation is superseded and must be removed.

## Considered Approaches

1. **Keep the native popover.** This preserves its animation and automatic behavior, but cannot
   keep the entire visible surface below the menu bar. It does not meet the reported requirement.
2. **Add content padding or a positioning offset.** This moves content inside the same native
   chrome and leaves the visible glass overlap unchanged. It is rejected.
3. **Use a directly positioned nonactivating panel.** This gives Needlbar ownership of the visible
   bounds while preserving the current SwiftUI content and data flow. This is the approved approach.

## Presentation Boundaries

`MenuBarController` remains responsible for choosing the Overview or provider SwiftUI content.
It no longer owns an `NSPopover` or implements `NSPopoverDelegate`. Presentation is delegated to
one injected `MenuPanelPresenting` object:

```swift
@MainActor
protocol MenuPanelPresenting: AnyObject {
    var isShown: Bool { get }
    var onDismiss: (@MainActor () -> Void)? { get set }

    @discardableResult
    func present(
        _ contentViewController: NSViewController,
        anchoredAt anchor: StatusItemPresentationAnchor
    ) -> Bool

    func dismiss()
}
```

Each status item exposes its own anchor rather than presenting a window itself:

```swift
struct StatusItemPresentationAnchor: Equatable {
    let buttonFrameInScreen: NSRect
    let visibleFrameInScreen: NSRect
}

@MainActor
protocol StatusItemHandle: AnyObject {
    var title: String { get set }
    var action: (@MainActor () -> Void)? { get set }
    func presentationAnchor() -> StatusItemPresentationAnchor?
}
```

The AppKit handle converts the real button bounds through its own window and uses that exact
window's screen:

```swift
let buttonFrame = window.convertToScreen(button.convert(button.bounds, to: nil))
let visibleFrame = window.screen?.visibleFrame
```

There is no `NSScreen.main` fallback. If an anchor cannot be resolved, presentation fails without
installing event monitors, and a temporary deep-link status item is removed immediately.

## Panel and Appearance

`AppKitMenuPanelPresenter` owns one reusable borderless `NSPanel` configured with
`.nonactivatingPanel`. The panel is clear and non-opaque, appears at `.popUpMenu` level, follows
the active Space, and can become key only when an embedded control needs interaction. It does not
activate Needlbar merely to show usage.

The current `OverviewPopoverView` and `ProviderPopoverView` remain unchanged. A hosting controller
is measured with `fittingSize` after layout, preserving their existing 300-point content width.
The host is wrapped in an `NSVisualEffectView` using the popover material, with an 18-point rounded
corner and a subtle one-point inner border. The panel uses no native popover arrow and no external
window shadow because either can visibly extend into the menu bar. Horizontal centering below the
clicked icon provides the association instead.

## Placement Contract

Placement is a pure function of the measured content size and the status item's anchor. With a
6-point horizontal and lower-screen margin, presentation first requires the measured content to
fit inside that inset visible frame. Oversized content fails presentation instead of crossing a
display boundary. For a fitting size:

```swift
let desiredX = anchor.buttonFrameInScreen.midX - contentSize.width / 2
let minimumX = anchor.visibleFrameInScreen.minX + 6
let maximumX = anchor.visibleFrameInScreen.maxX - 6 - contentSize.width
let x = min(max(desiredX, minimumX), maximumX)

let top = min(anchor.buttonFrameInScreen.minY, anchor.visibleFrameInScreen.maxY)
let desiredY = top - contentSize.height
let minimumY = anchor.visibleFrameInScreen.minY + 6
let maximumY = anchor.visibleFrameInScreen.maxY - contentSize.height
let y = min(max(desiredY, minimumY), maximumY)
```

The resulting panel's `maxY` can never exceed the clicked display's `visibleFrame.maxY`. With
normal horizontal space, its center equals the clicked icon's center. Near a display edge, keeping
the whole panel inside that display takes precedence. Negative and offset coordinates used by
secondary displays remain valid because the calculation never consults the primary display.

## Interaction and Lifecycle

- Clicking an icon while its panel is open toggles it closed.
- Clicking another Needlbar icon replaces the content and reanchors the same panel.
- A global mouse-down monitor retains the already verified desktop/other-app dismissal behavior.
- A presenter-owned local monitor dismisses only clicks outside the panel and passes the event on.
- Escape and application deactivation dismiss the panel.
- Settings and provider authentication actions dismiss first, then run the existing action.
- Retry does not dismiss the panel.
- `dismiss()` is idempotent and invokes `onDismiss` once per visible presentation.
- A monotonically increasing presentation generation prevents an old async refresh or queued
  monitor callback from closing or replacing a newer presentation.
- `onDismiss` cancels monitors and removes a temporary deep-link status item exactly once.
- `stopObserving()` dismisses the panel and releases all monitoring resources.

## Test and Native Acceptance

Implementation is test-first. Pure geometry tests must cover the recorded native coordinates,
both horizontal edges, the lower visible-frame boundary, and a secondary display with offset or
negative coordinates. Controller tests must cover anchor forwarding, toggle/reanchor behavior,
failed presentation cleanup, monitor installation only after success, stale callbacks, ordered
Settings/authentication dismissal, and temporary deep-link cleanup. Presenter tests must cover
idempotent dismissal and local inside/outside event classification.

A separately signed candidate must then be inspected on the current Mac. Acceptance requires:

1. the entire visible panel, including its background, starts below the menu-bar boundary;
2. the panel is horizontally centered below the clicked Needlbar icon when space permits;
3. Settings and provider buttons receive clicks;
4. desktop, another-app, same-app-outside, Escape, and app-switch actions dismiss it;
5. the active candidate process remains healthy;
6. a secondary-display check uses the clicked button's display and remains on-screen.

The actual macOS 14 arm64 acceptance gate remains separate.

## Non-Goals

- Changing Overview/provider content, metrics, authentication, notifications, widgets, or exports.
- Adding a decorative arrow, detachable window, drag behavior, resize behavior, or persistence.
- Using primary-screen coordinates or hard-coded macOS 26 dimensions.
- Pushing, tagging, notarizing, publishing, or mutating the Apple developer portal.
