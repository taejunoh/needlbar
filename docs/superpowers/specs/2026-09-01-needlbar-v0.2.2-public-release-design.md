# Needlbar v0.2.2 Public Release Design

**Status:** Approved design for the public v0.2.2 release.  
**Scope:** Versioning, public-release documentation, tag-triggered signing and
publication, and downloaded-artifact verification only. This adds no product,
provider, analytics, export, widget, or notification capability.

## 1. Release statement and baseline

Needlbar v0.2.2 is the first public release in this release line. The public
version is exactly `0.2.2`; the annotated Git tag is exactly `v0.2.2`.

Both distributable bundles must identify the same release:

| Bundle | `CFBundleShortVersionString` | `CFBundleVersion` |
| --- | --- | --- |
| `Resources/Info.plist` host app | `0.2.2` | `2` |
| `WidgetExtension/NeedlbarWidgetExtension-Info.plist` | `0.2.2` | `2` |

The host and widget version values are changed together. The macOS 14 minimum,
arm64 distribution target, bundle identifiers, App Group identifiers, signing
identity requirements, and extension-first signing order remain unchanged.

This public release is made from the later exact green `main` commit selected
at release time, not from a historical validation commit. The signed tagless RC
run [33524771615](https://github.com/taejunoh/needlbar/actions/runs/33524771615)
at source `15c229f` and the latest documentation CI run
[33526409582](https://github.com/taejunoh/needlbar/actions/runs/33526409582)
are pre-release evidence only. They neither name nor authorize the public
release commit.

## 2. Public README contract

The README has two truthful release phases selected offline by the exact STATUS
heading `## v0.2.2 Public Release Record — 2026-09-01`.

Before the tag is made and until public verification completes, release source
uses the **prepared** phase. Its Availability section must contain this exact
sentence and must not contain the public-availability sentence:

```text
Needlbar v0.2.2 is prepared for public release for macOS 14 or later on Apple Silicon.
```

The prepared phase keeps this future link visible:

```markdown
[Download Needlbar v0.2.2 for Apple Silicon](https://github.com/taejunoh/needlbar/releases/download/v0.2.2/Needlbar-macos-arm64.zip)
```

Prepared copy states that the future ZIP is for macOS 14 or later and Apple
Silicon and will be Developer ID-signed and notarized, but that the link becomes
active only after the tag-triggered workflow publishes the matching asset. It
does not claim present availability or downloadability. It must not imply that a
source-built `make package` archive is the public artifact: local packaging
stays an ad-hoc evaluation path.

Only after the tag workflow has both successful `validate` and successful
`publish` jobs and fresh Release assets pass Section 6 verification does the
README enter the **public** phase. It then contains this exact sentence and no
longer contains the prepared sentence:

```text
Needlbar v0.2.2 is publicly available for macOS 14 or later on Apple Silicon.
```

Public copy states that the linked ZIP is Developer ID-signed and notarized.

The v0.2.2 Analytics section uses prepared-for-public-release wording in the
prepared phase and released wording only in the public phase, without changing
its local-only, manual, fixed 30-day, no-history, no-network,
no-provider-authentication, and no-remote-forge boundaries. v0.2.0 export
semantics and v0.2.1 widget/notification behavior remain unchanged.

The README must preserve this v0.2.1 caveat verbatim in meaning and scope:

> Native signed macOS 14 arm64 Widget Gallery/App Group and
> notification-permission acceptance still require external evidence; the local
> macOS 26 build is not that acceptance.

Public availability does not convert this unresolved native acceptance into a
claim of Widget Gallery discovery, App Group runtime, deep-link, notification,
or macOS 14 validation.

## 3. Documentation-shell regression contract

`scripts/tests/notarize-app-tests.sh` owns the documentation-shell contract.
It first adds a phase-aware RED test and then updates `README.md` and the
checker together. The test selects phase solely from the presence of the exact
`## v0.2.2 Public Release Record — 2026-09-01` STATUS heading:

1. without that heading, README requires the exact prepared sentence and
   rejects the exact public-availability sentence;
2. with that heading, README requires the exact public-availability sentence
   and rejects the exact prepared sentence;
3. in both phases, README contains the exact `v0.2.2` Apple Silicon ZIP URL
   from Section 2 and the applicable Developer ID/notarization wording;
4. in both phases, README retains the local source-build/ad-hoc distinction and
   the exact v0.2.1 macOS 14 Widget Gallery/App Group acceptance caveat;
5. in both phases, README retains the Cursor boundary sentence: “Needlbar does
   not use Cursor credentials, cookies, private endpoints, or remote usage
   hydration.”
6. The historical `docs/STATUS.md` sections remain historical evidence. Their
   tagless RC and pre-release statements must not be rewritten to claim that
   those older runs created a public release, nor may the checker require
   historical text to describe a future release.

The contract test must include phase-mismatch decoys plus malformed README
decoys that omit either the exact release URL, the Cursor privacy sentence, or
the v0.2.1 caveat. The checker must reject each decoy. It may not weaken the
existing Cursor/privacy or STATUS-history assertions merely to accommodate
prepared or public wording.

## 4. Release workflow and artifacts

The existing tag-triggered `release.yml` remains the release executor. A push
of `refs/tags/v0.2.2` starts `validate`; only a successful validation enables
the existing tag-only `publish` job. `workflow_dispatch` remains tagless
validation and never publishes a GitHub Release.

Validation must, in order:

1. check out the exact tag commit and recursive submodules on macOS 14 with
   the pinned Swift/Xcode selection;
2. run `make test`, `make package`, and `make smoke`;
3. sign, notarize, staple, and Gatekeeper-validate the arm64 app with the
   protected `release` environment;
4. revalidate the stapled app after extracting the final ZIP; and
5. upload only the verified ZIP and a checksum sidecar named
   `Needlbar-macos-arm64.zip.sha256`.

The checksum sidecar is a single SHA-256 line for the exact ZIP filename.
The publish job downloads only these validated outputs from the same workflow
run and creates/updates the GitHub Release for `v0.2.2` with both files. It
does not rebuild, re-sign, notarize, or substitute an artifact.

Release notes are concise and limited to:

- v0.2.0: local JSON snapshot export;
- v0.2.1: Overview widget and opt-in quota notifications, with the unresolved
  native macOS 14 Widget Gallery/App Group acceptance caveat; and
- v0.2.2: manual local repository cost analytics over automatically observed
  workspaces.

They must not claim cloud sync, a Needlbar account, telemetry, remote Git or
forge access, provider changes, Cursor quota collection, or an accepted
macOS 14 widget runtime.

## 5. Exact tag gate

After all release-source changes are committed, the maintainer runs the focused
documentation-shell test, then `make test`, `make package`, and `make smoke`
from `main`. The full commit SHA produced by those green commands is the sole
candidate release SHA `G`.

Before creating a tag, all checks below must pass:

```bash
git switch main
git pull --ff-only origin main
git status --porcelain
git rev-parse HEAD
git tag -l v0.2.2
git ls-remote --tags origin refs/tags/v0.2.2
```

`git status --porcelain` must be empty; local and remote tag lookups must show
that `v0.2.2` is absent; and `HEAD` must equal recorded `G`. The maintainer then
creates an annotated tag on that exact object:

```bash
git tag -a v0.2.2 G -m "Needlbar v0.2.2"
git rev-parse v0.2.2^{}
git show --no-patch --format=fuller v0.2.2
git push origin v0.2.2
```

The resolved tag object must equal `G` before the push. Only this tag is pushed;
the release is never created by a local `gh release create` or a second manual
upload.

## 6. Post-publication verification

After the workflow reaches both successful `validate` and successful `publish`,
verification uses the Release asset, not a retained Actions artifact or local
`dist` file.

1. Confirm the GitHub Release is for `v0.2.2` and contains exactly the public
   ZIP and its `.sha256` sidecar; download both into a fresh temporary directory.
2. Run `shasum -a 256 -c Needlbar-macos-arm64.zip.sha256`; the filename and
   digest must match the downloaded ZIP.
3. Extract the ZIP into a fresh temporary directory. Confirm the host app and
   widget executable are arm64 and both Info.plists contain `0.2.2`/`2`.
4. Run `codesign --verify --deep --strict --verbose=2`, inspect the configured
   Developer ID identity and hardened-runtime flags, run `xcrun stapler
   validate`, and run `spctl --assess --type execute --verbose` on the extracted
   app.
5. Run the packaged-app smoke check against that downloaded, extracted app
   without replacing the release asset. Record only safe command outcomes,
   version, checksum, and run/release URLs; never record certificate, account,
   token, keychain, or app-specific-password values.

The verification result must distinguish a completed public release from the
older tagless RC evidence and must retain the v0.2.1 native acceptance caveat.

## 7. Failure rules

Any failed pre-tag check stops before tag creation. Any failed validation,
notarization, staple, Gatekeeper, upload, publish, checksum, identity, runtime,
or downloaded-asset smoke check stops release completion reporting.

Failure never rewrites, force-moves, deletes, or recreates `v0.2.2`; it never
deletes or edits a GitHub Release to conceal a failed attempt. The exact failed
stage and safe run URL may be recorded. A follow-up release requires an
explicitly chosen corrective version/tag strategy; it must not silently reuse
or retarget a public tag.

## 8. Exclusions

This release work does not add or change providers, authentication, credentials,
Cursor session handling, Cursor remote hydration, private endpoints, quota
collection, analytics data flow, export contents, widget data flow,
notifications, telemetry, backend services, or Git/forge behavior. It does not
claim to complete the outstanding v0.2.1 native macOS 14 Widget Gallery/App
Group acceptance.

## 9. Acceptance criteria

1. Host and widget bundle versions are exactly `0.2.2` and `2`.
2. README has the exact public release URL and truthful phase-appropriate
   wording while retaining the required v0.2.1, Cursor, local-package, and
   local-only boundaries.
3. Documentation-shell tests prove the phase-aware contract and reject
   weakened privacy/caveat/history decoys.
4. The selected green `main` SHA is tagged once with an annotated `v0.2.2` tag
   after absence, head, and clean-worktree checks.
5. The tag-triggered workflow validates, signs, notarizes, staples,
   Gatekeeper-validates, uploads, and then publishes the exact validated ZIP
   and checksum sidecar.
6. A fresh downloaded Release asset passes checksum, architecture, bundle
   version, identity, hardened-runtime, staple, Gatekeeper, and smoke checks.
7. Any failure stops without tag/release rewriting or deletion.
8. No unrelated feature or provider behavior changes.
