# Needlbar v0.3.0 Release and Homebrew Cask Design

**Status:** Draft for written-spec review. The user has approved the release
direction; this document does not authorize implementation, signing, tagging,
publication, tap writes, or credential use.

**Scope:** Freeze the already implemented v0.3 surface for a new public
`v0.3.0` release, use the existing signing and verification pipeline, and add
one Homebrew Cask only after that release has independently passed public
artifact verification. This is a distribution change, not a Phase 2 Settings
feature or product redesign.

## 1. Release baseline and frozen product scope

The next release is exactly version `0.3.0`, with annotated tag `v0.3.0`.
Both distributable bundles change together:

| Bundle | `CFBundleShortVersionString` | `CFBundleVersion` |
| --- | --- | --- |
| Host `Resources/Info.plist` | `0.3.0` | `3` |
| `WidgetExtension/NeedlbarWidgetExtension-Info.plist` | `0.3.0` | `3` |

The release includes only the v0.3 functionality already implemented on the
selected release commit: the local system-monitor/dashboard and the existing
Settings Module Studio Phase 1 integration. It preserves the approved
local-first, provider, export, widget, notification, privacy, and bridge
boundaries. Phase 2 Settings styles/units, new providers, new credentials,
new telemetry, a backend, an app updater, and unrelated refactors are out of
scope.

The committed `vendor/tokscale-core` revision is unchanged. Initialize that
pinned revision normally in an isolated worktree; do not alter the existing
dirty main-worktree vendor checkout or bump the committed dependency.

The macOS 14 minimum, Apple-Silicon-only target, bundle identifiers, App Group
identifiers, extension-first signing order, and Developer ID requirements are
unchanged. The public archive remains `Needlbar-macos-arm64.zip`, containing
`Needlbar.app` at the ZIP root and exactly one embedded WidgetKit extension.

## 2. Truthful release state and non-claims

Until public verification completes, documentation calls v0.3.0 prepared for
release, not publicly available. The existing public v0.2.2 record remains
historical evidence and is never rewritten to suggest that it contains v0.3.0
features or was produced by the v0.3.0 process.

Only after the `v0.3.0` tag run publishes the Release and a fresh download of
its assets passes the checks in Section 4 may README/public documentation name
v0.3.0 as publicly available and link its immutable release URL.

This release must retain the known limits rather than convert release status
into an acceptance claim:

- Native macOS 14 arm64 Widget Gallery/App Group and notification-permission
  acceptance remains pending external evidence.
- The current v0.3 native review is partial: keyboard/drag, display-transition,
  full accessibility, and the previously unobserved Codex verifying UI phase
  are not passed merely because automated tests or a signed release pass.
- Any provider-specific acceptance or compatibility item recorded as pending in
  `docs/STATUS.md` remains pending unless separately observed and recorded.

The README and fixed v0.3.0 release notes may describe implemented v0.3
behavior, but must not claim the pending items above, a Mac App Store release,
automatic in-app updates, cloud services, telemetry, or Cursor quota support.

## 3. Two-run release boundary

The current release workflow remains the sole signing and publication executor.
It is used in two deliberately separate runs:

1. A maintainer manually dispatches tagless validation for the exact candidate
   source commit `G`. It runs the existing macOS 14/Swift 6 checks, `make test`,
   `make package`, and `make smoke`, then the protected-environment Developer ID
   signing, notarization, stapling, Gatekeeper, and extracted-archive checks.
   It uploads a validation artifact but never creates a tag or public Release.
2. After the tagless run is successful and `G` is otherwise accepted as the
   release candidate, the maintainer performs clean-worktree/tag-absence checks,
   creates one annotated `v0.3.0` tag on exactly `G`, and pushes only that tag.
   The tag-triggered run independently rebuilds and independently verifies its
   own artifact before publication.

A successful tagless artifact is evidence for its own run only. It is not
assumed byte-identical to, substituted for, or uploaded as the later
tag-triggered artifact.

The tag-triggered `publish` job must continue to receive only the verified ZIP
and checksum produced by its same workflow run. It must not rebuild, re-sign,
notarize, invoke `gh`, locally upload assets, or substitute an artifact. The
release notes body is version-specific and checked in for `v0.3.0`; historical
v0.2.2 release notes remain unchanged.

No release secret names, credentials, temporary-keychain lifecycle, certificate
handling, hardened-runtime check, timestamp behavior, App Group substitution,
or signing order change as part of this work.

## 4. Artifact and post-publication verification

The tag run can publish only these v0.3.0 assets:

- `Needlbar-macos-arm64.zip`
- `Needlbar-macos-arm64.zip.sha256`

The sidecar contains one SHA-256 record for exactly the ZIP filename. Before a
Homebrew Cask is authored, a maintainer downloads both files afresh from the
public `v0.3.0` GitHub Release into a clean directory and verifies all of the
following against that download, not an Actions artifact or local `dist`:

1. `shasum -a 256 -c Needlbar-macos-arm64.zip.sha256` succeeds.
2. Extraction yields `Needlbar.app`; host and embedded-widget executables are
   arm64; both Info.plists report `0.3.0` and build `3`; and no standalone
   review-host executable or acceptance-fixture file/parser is present in the
   public bundle. The production passive Settings preview remains included.
3. The extracted bundle passes strict deep code-signature verification, has the
   configured Developer ID authority and hardened runtime, passes `xcrun
   stapler validate`, and passes `spctl --assess --type execute --verbose`.
4. The packaged-app smoke check passes against the downloaded, extracted app
   without modifying the Release asset.

Safe evidence may record version, checksum, run/release URL, and command
outcome. It never records certificate material, Apple ID, passwords, tokens,
Keychain contents, or other credentials. A failure stops the release completion
claim; it must not force-move, delete, recreate, or silently retarget the tag or
published release.

## 5. Homebrew boundary after verification

Only after Section 4 passes, add `Casks/needlbar.rb` to the existing
`taejunoh/homebrew-tap`. That one external tap file is the entire initial
Homebrew integration boundary.

The Cask must:

- declare version `0.3.0`;
- fetch the immutable v0.3.0 GitHub Release URL for
  `Needlbar-macos-arm64.zip`, not a branch, source archive, Actions artifact,
  redirecting "latest" URL, or local `dist` path;
- use the SHA-256 computed from the freshly downloaded public ZIP;
- install `Needlbar.app` from the ZIP root;
- declare macOS 14 (Sonoma) or later and actively reject Intel installations
  with Homebrew's supported arm64 dependency/architecture declaration, rather
  than merely selecting an arm64 URL; and
- preserve user data by omitting any default `zap`, `trash`, or equivalent
  cleanup declaration.

The initial Cask has no automatic tap-writing workflow, no release credential,
no GitHub token or secret, no `livecheck`/automatic version bump process, and
no auto-update or Sparkle/appcast integration. Cask updates are later manual,
versioned tap changes made only after each new public release has completed the
same fresh-download verification. Until a separately approved updater design
exists, Homebrew users update through `brew upgrade`; Needlbar itself does not
claim or implement application self-update.

The Cask must comply with Homebrew's Cask and tap guidance, including its
supported macOS/architecture dependency syntax and immutable artifact checksum
requirements. Authoritative references are the [Homebrew Cask
Cookbook](https://docs.brew.sh/Cask-Cookbook) and [How to Create and Maintain a
Tap](https://docs.brew.sh/How-to-Create-and-Maintain-a-Tap).

## 6. Regression contracts and historical integrity

Implementation must extend the existing release/documentation shell contracts
with explicit v0.3.0 assertions. The contracts must check host and widget
version/build values together, v0.3.0 URL and asset names, v0.3.0-specific
release-notes selection, prepared-versus-public wording, no-preview-fixture
public-package rules, and the existing notarization/extracted-archive checks.

Current-release assertions must move to v0.3.0 while preserving historical
v0.2.2 fixtures and their integrity checks. Do not rewrite fixed v0.2.2 release
notes, STATUS history, recorded checksum, release URL, or claims. Tests must reject
cross-version mismatches (for example, a v0.3.0 version with a v0.2.2 URL or
notes body), an incorrect build number in either bundle, Intel-permissive Cask
metadata, a mutable Cask URL, a checksum copied from a non-public artifact, and
any default data-deleting zap behavior.

Validate the Cask with the installed Homebrew's supported style/audit checks
and an actual install into an isolated application directory. Verify the
installed bundle against the public download, then remove only that test
installation without zap. Do not replace the user's running development app,
reset preferences, or suppress Gatekeeper to make this check pass. Record
tool-version-specific audit limitations separately from successful checks.

The v0.3.0 release/tap contract is successful only when it preserves the
existing signed-release security boundary and the historical v0.2.2 record
while truthfully exposing the distinct v0.3.0 artifact.

## 7. Acceptance criteria

1. The selected, clean candidate commit contains no Phase 2 or unrelated scope
   change and keeps the pinned vendor revision unchanged.
2. Host and widget identify exactly `0.3.0`/`3`.
3. A tagless validation of exact candidate `G` succeeds without creating a
   public release; the later tag run independently validates its own artifact.
4. Exactly one annotated `v0.3.0` tag points to `G`; the tag release contains
   only the validated ZIP and its matching SHA-256 sidecar.
5. A fresh public download passes checksum, arm64, version, fixture exclusion,
   Developer ID/hardened-runtime, staple, Gatekeeper, and smoke checks.
6. Only then does `taejunoh/homebrew-tap` receive the single immutable,
   SHA-pinned, macOS-14+/arm64-only `needlbar` Cask with no default data zap.
7. Documentation and tests preserve the v0.2.2 historical record and state all
   pending macOS 14/native acceptance limits without upgrading them to passes.
